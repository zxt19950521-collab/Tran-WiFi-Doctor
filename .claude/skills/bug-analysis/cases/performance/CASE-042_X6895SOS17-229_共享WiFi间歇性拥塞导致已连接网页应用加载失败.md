# CASE-042: 共享 WiFi 间歇性拥塞导致"已连接但网页/应用加载失败"（强信号，系统已验证）

## 基本信息
- **案例ID**: CASE-042
- **分类**: performance
- **来源**: X6895SOS17-229（粉丝反馈 450028754，TagLog ×2 / Normal / Subsyslog，无 tcpdump、无空口）
- **创建时间**: 2026-10-16
- **匹配次数**: 0

## 现象描述
- 粉丝反馈（肯尼亚）：WiFi 已连接，但网页和其他应用无法正常加载；偶现
- 机型 Infinix X6895（XOS 17 / Android 17，MTK 平台）
- 连接共享/社区 WiFi "Uplink-Amanda"（同区域有 "Uplink-Lion"、"Uplink-Dylan" 等同系列 SSID）
- 系统侧网络始终 `VALIDATED`，无断连、无漫游，状态栏无感叹号，用户无"网络差"提示

## 根因结论

**网络侧（AP / 网关 / 回程）间歇性严重拥塞，下行回包秒级排队；手机侧收发正常。**

判定为网络侧（非手机射频/驱动/省电）的依据：
1. 问题时段手机 ICMP/DNS 请求约 10ms 内即被 AP ACK（`wlanPktTxDone ... Status[0]`），但回包延迟 1~12 秒，部分 DNS 无应答；正常时段 DNS 中位 RTT 9ms
2. 同时段 RSSI -35 ~ -50 dBm、速率 650/722 Mbps、`TxTimeOut=0`、`AwakeDur`≈1024ms/s（全程唤醒）
3. 拥塞时段信道空闲 slot 中位数下降约 5 倍，PER（16% vs 6%）、ACK fail（8.4/s vs 3.1/s）约升 3 倍；网关持续 ARP 扫描大量地址，为多终端共享热点 —— 空口争用为伴随/加重因素（同 CASE-008），但秒级时延远超空口重传量级，主因在 AP/网关/回程排队
4. 系统无提示原因：`TranWifiSmartAssistantController` 测速超时后启动 revalidation，但框架 HTTP 探测耗时 6.2s 仍返回 200，revalidation 被 `framework_pass` 取消

局限：无 tcpdump，未区分 AP/网关拥塞与运营商回程拥塞。

## 排查步骤
1. main log 查 `WifiStatistics:WifiNetworkCheck: Ping result: {success=false`、`WifiStat:NetworkProbe: Ping unexpected`、`Speedtest unexpected`、`record probe result ... highDelay=true`，定位异常时段
2. 用户版本无 `wpa_supplicant` / `NetworkMonitor` 日志时，以厂商 `WifiStatistics` / `WifiStat` / `TranWifiSmartAssistantController` 日志为主
3. kernel log 用 `android time ... UTC` 标记换算当地时间（无 MTK converter 时）
4. 配对 `statsParseICMPInfo` TX/RX（按 Id）、`statsParseDNSInfo` TX/RX（按 TransID）计算 RTT，统计慢应答与无应答
5. 查 `wlanPktTxDone ... Status[0]` 及 `Hif~Done` 时延，确认请求已被 AP 及时 ACK（排除手机发送侧）
6. 对比 `mtk_cfg80211_get_station`（RSSI、速率、TxTimeOut）与 `wlanLinkQualityMonitor`（PER、idle slot、AwakeDur）在正常/拥塞时段的差异
7. 查 `ConnectivityInputLogger ... VALIDATED` 与 `cancel revalidation session: framework_pass`，解释用户无感知
8. 排除项：`GetAddrInfoHandler::run: network access blocked` 仅涉及后台应用（WPS、CapCut 等），属正常后台限制

## 解决建议
1. 按网络环境问题回复：共享 WiFi 高峰拥塞；同一 WiFi 用其他手机对比，或切换其他 WiFi / 移动数据确认
2. 需区分 AP/网关拥塞与回程拥塞时：复现抓 tcpdump，同时 ping 网关与公网
3. 体验优化（WiFi 智能助手/框架评估）：将 HTTP 探测耗时过长（如 >3s）或连续 ping/DNS 超时纳入"网络质量差"判定，提示用户或智能切换移动数据
