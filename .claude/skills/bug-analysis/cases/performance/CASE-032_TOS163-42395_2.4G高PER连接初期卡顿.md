# CASE-032: 2.4G 连接初期 PER 极高导致体验卡顿（叠加 WiFi 长时间关闭）

## 基本信息
- **案例ID**: CASE-032
- **分类**: performance
- **来源**: TOS163-42395
- **创建时间**: 2026-08-12
- **匹配次数**: 0

## 现象描述
- 粉丝反馈（原声）：*When i used wifi the mobile phone was logging*（推测为 lagging，卡顿）
- 机型 TECNO CN6，HiOS 16.3.0，菲律宾（Asia/Manila）
- 只出现一次；申报时间 2026-07-12 12:11:20（Manila）
- 连接 SSID `RAQUEL PARDILLA`，**2.4GHz Channel 2（2417MHz）**
- 表象：用户认为“用 WiFi 时手机卡顿”，但日志显示问题发生在 **WiFi 刚手动开启后的连接初期**

## 根因结论
**2.4G Channel 2 信道质量差，连接后前 30 秒 `wlanLinkQualityMonitor` 的 PER 均值 28.5%、峰值 90%，Tx fail/ACK fail 飙升、物理速率被压低，导致体验卡顿；同时 WiFi 此前关闭约 1 小时+，叠加无网络感知。**

机理链条：
1. WiFi 至少从 10:58 到 12:06:26 处于 OFF，OFF 期间大量 `ERR_INTERNET_DISCONNECTED`
2. 用户 12:06:26 通过 SystemUI 手动 `setWifiEnabled=true`，12:06:31 完成 assoc + 4-Way Handshake
3. 连接后前 30s（12:06:34~12:07:04）PER 极高：均值 **28.5%**、峰值 **90%**，PER≥30% 占比 43%
4. 同期 Tx rate 仅 130~390 Mbps，Tx fail 累积快、ACK fail / RTS fail 高 → 空口重传/丢包严重
5. 30s 后 PER 均值降至 **11.0%**，RSSI 从 -69~-71 改善到约 -40 dBm，但仍有间歇 PER≥30%
6. 全时段 Tx 总失败率 **10.2%**（6253/61499）——按 MTK 规则 >10% 属异常
7. 框架层 Ping 多数成功（26 ok / 2 fail，均值 47ms），易误判为“链路正常”，**必须看 kernel PER**

## 排查步骤（学习要点：必须量化 PER）
1. main_log 确认 WiFi OFF→ON 时间线与 `CTRL-EVENT-CONNECTED` / `Wifi network validated`
2. **kernel_log（`.localtime`）提取 `wlanLinkQualityMonitor` 的 PER 序列**，按时段统计：
   - PER 均值 / 峰值 / PER≥30% 占比
   - Tx fail 率 = fail/total；ACK fail、RTS fail 是否同步升高
   - Tx/Rx rate 是否被压低
3. 对齐 RSSI（main `====>>rssi` 或 kernel get_station）：初始弱信号 + 2.4G 干扰 → 高 PER
4. 勿仅凭 Ping 成功/validated 下“WiFi 正常”结论——本案 Ping 尚可但 PER 已异常

### PER 判读参考（MTK Link Quality）
| PER | 含义 |
|-----|------|
| < 10 | 基本正常 |
| 10~30 | 偏高，体验可能抖动 |
| ≥ 30 | 明显异常，易卡顿 |
| ≥ 50~90 | 严重，接近不可用 |

配套：Tx fail 率 >10% 异常；retry 率 >20% 较差、>40% 严重。

## 建议措施
1. **分析硬规则**：有 `wlanLinkQualityMonitor` 时必须统计 PER 均值/峰值/≥30% 占比，不可只报 Ping/RSSI
2. 用户侧：优先连 5GHz；避开 Channel 2 拥塞；改善 AP 位置/减少同频干扰
3. 复测：建议补 tcpdump / 空口 / picus，区分 AP 侧干扰 vs 终端 RF

## 数据局限
- kernel 仅覆盖 WiFi ON 后约 5 分钟；缺 tcpdump、空口、picus 有效数据
- PER 高可坐实空口差，但根因（AP 干扰 vs 终端）需空口进一步确认
